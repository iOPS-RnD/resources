== Purpose

This repository contains **shared public resources for the iOPS — Intelligent Operated Power System R&D initiative**.

The resources maintained here are intended to support multiple iOPS projects rather than a single project or software component.

The repository provides a common place for reusable knowledge, architecture, conventions, diagrams, examples, templates and other material that should remain available independently of the lifecycle of an individual R&D project.

Project-specific source code, datasets, documentation and results should normally remain in the corresponding project repository.

The content is read and edited in the link:https://github.com/iOPS-RnD/resources/wiki[resources wiki].

The initiative, its projects, shared research assets and software are presented on the link:https://github.com/iOPS-RnD[iOPS-RnD organisation page].

== Scope of this repository

Material belongs in `resources` when it is useful across **two or more iOPS projects** or represents a common iOPS convention.

Typical content includes:

=== Architecture and concepts

* common iOPS reference architecture;
* DataOps, ModelOps and SchemaOps concepts;
* knowledge-graph architecture;
* AI and LLM architecture;
* validation architecture;
* data-space concepts;
* digital-twin concepts;
* common service patterns;
* data and application discovery.

=== Information modelling and standards

* CIM usage guidance;
* CGMES and Network Code profile guidance;
* RDF and RDFS conventions;
* SHACL conventions;
* JSON-LD conventions;
* DCAT dataset metadata;
* PROV-O provenance;
* GeoSPARQL;
* IEC 61850 alignment;
* BIM/IFC alignment;
* cross-standard modelling patterns.

This repository should reference authoritative standards and repositories rather than duplicate externally maintained standards artefacts.

=== Data and model conventions

Shared conventions can include:

* dataset identification;
* model identification;
* metadata;
* provenance;
* versioning;
* timestamps and time horizons;
* model authority;
* validation status;
* namespace conventions;
* URI patterns;
* serialisation conventions;
* synthetic-data conventions.

=== Diagrams

Reusable diagrams illustrating:

* architecture;
* information flows;
* semantic models;
* service interaction;
* DataOps, ModelOps and SchemaOps;
* validation;
* AI integration;
* geospatial concepts;
* digital twins.

Where practical, both the editable source and a rendered representation should be stored.

=== Examples

Small reusable examples may be maintained here when they demonstrate a concept shared by several projects.

Examples should be:

* synthetic;
* non-sensitive;
* understandable without access to internal Statnett systems;
* based on open standards;
* small enough to be useful for documentation and testing.

Large or independently versioned datasets should have their own repositories.

=== Templates

Reusable templates may include:

* repository structure;
* README documentation;
* architecture documentation;
* project technical documentation;
* dataset documentation;
* metadata;
* demonstrations;
* validation plans;
* release documentation.

=== Training and dissemination

The repository can contain common public material used to explain iOPS concepts, including:

* tutorials;
* workshop material;
* public presentations;
* demonstrations;
* introductory material;
* diagrams used across several projects.

Project-specific publications and deliverables should remain with the corresponding project.

=== Branding

Common iOPS branding can include:

* iOPS logos;
* presentation assets;
* common diagrams;
* graphical conventions.

Project-specific branding can be referenced from here but should normally remain with the project.

== What does not belong here

The `resources` repository is intentionally **not a catch-all repository**.

The following should normally be stored elsewhere:

[cols="1,2"]
|===
|Content |Location

|Project-specific source code
|Project repository

|Reusable software library
|Dedicated software repository

|Large or independently maintained dataset
|Dedicated data/model repository

|Project-specific research result
|Project repository

|Project planning and reporting
|Project or private management repository

|Programme management
|Private iOPS management repository

|Partner-confidential information
|Approved protected environment

|Operational grid information
|Approved protected environment

|Credentials, tokens or secrets
|Never store in this repository
|===

== Relationship to external standards and repositories

iOPS builds on open standards and existing industry initiatives rather than reproducing them.

Where an authoritative source exists, iOPS documentation should link to and use that source rather than maintain an unnecessary copy.

The standards and other references cited in this repository are listed in link:references/README.adoc[references/].

== Guiding principles

Shared iOPS resources should follow a few basic principles.

=== Standards first

Prefer established international and industry standards over project-specific formats and concepts.

=== Machine-readable as well as human-readable

Where appropriate, information should be made available in forms that can be processed directly by applications and AI systems in addition to conventional documentation.

=== Reusable beyond one project

Material placed here should be useful independently of the project where it originated.

=== Preserve provenance

When material originates in an R&D project, the origin should remain visible even when the material becomes a shared iOPS resource.

=== Do not duplicate authoritative sources

Reference externally governed specifications, schemas and vocabularies instead of creating diverging local copies.

=== Synthetic before sensitive

Examples and demonstrations should use synthetic or otherwise publishable information wherever possible.

== Contribution

Content is edited in the wiki. Edits are proposals and are reviewed before they become part of the iOPS resources. Repository files are generated; do not edit them directly.
